# Сборка и публикация

## Локально

```bash
npm install
npm start          # собрать и открыть на http://localhost:4173
npm run dev        # dev-сервер http://localhost:5173
npm run build      # tsc -b && vite build -> dist/
npm run preview    # отдать уже собранный dist/
npm run typecheck  # только типы
```

Сборка полностью статическая: `dist/` — это `index.html`, один JS и один
CSS. Ни сервера, ни переменных окружения в рантайме не требуется.

Способы запуска подробно, включая автономный HTML без сервера, —
в [08-local-run.md](./08-local-run.md).

## GitHub Pages

Публикацией занимается workflow
[`.github/workflows/deploy.yml`](../.github/workflows/deploy.yml):
он срабатывает на push в `main` (и вручную через «Run workflow»),
собирает проект и выкладывает `dist/` через официальные actions
`upload-pages-artifact` / `deploy-pages`. Ветка `gh-pages` не нужна.

### Адрес сайта

GitHub Pages различает два вида сайтов, и от этого зависит адрес и базовый
путь сборки:

| Что нужно               | Имя репозитория          | Адрес                                  | `BASE_PATH` |
| ----------------------- | ------------------------ | -------------------------------------- | ----------- |
| проектный сайт          | любое, например `kranTK` | `https://<владелец>.github.io/kranTK/` | `/kranTK/`  |
| корневой сайт владельца | `<владелец>.github.io`   | `https://<владелец>.github.io/`        | `/`         |

Workflow определяет это сам: если имя репозитория заканчивается на
`.github.io`, базовый путь `/`, иначе `/<имя репозитория>/`. Править
ничего не нужно — переименование репозитория подхватится автоматически.

**Чтобы стенд открывался как `krantk.github.io`**, нужен владелец с именем
`krantk` (личный аккаунт или организация) и в нём репозиторий с точно таким
же именем — `krantk.github.io`. Порядок действий:

1. Создать организацию `krantk` (New organization, тариф Free) — либо
   зарегистрировать аккаунт с этим именем.
2. Создать в ней **публичный** репозиторий `krantk.github.io`.
3. Добавить его как remote и запушить `main`:
   ```bash
   git remote add pages git@github.com:krantk/krantk.github.io.git
   git push pages main
   ```
4. В этом репозитории включить Pages (см. ниже) — сайт появится на
   `https://krantk.github.io/`.

Если менять владельца не хочется, самый короткий путь — оставить текущий
репозиторий и получить адрес вида `https://<владелец>.github.io/kranTK/`.

### Включение Pages — обязательный ручной шаг

**Settings → Pages → Build and deployment → Source: GitHub Actions.**

Сделать это нужно один раз для каждого репозитория, откуда публикуется
сайт. Автоматизировать не получится — см. следующий раздел.

Права для Actions уже объявлены в workflow (`pages: write`,
`id-token: write`), их трогать не нужно.

### Ошибки шага `configure-pages`

**`Get Pages site failed … Not Found`** — сайт Pages у репозитория ещё не
создан. Включить источником GitHub Actions в настройках (выше).

**`Create Pages site failed. Resource not accessible by integration`** —
попытка включить Pages автоматически через `enablement: true`. Так не
работает: создание сайта Pages — административная операция, а у
`GITHUB_TOKEN` прав администратора репозитория нет; `pages: write` даёт
право только публиковать в уже существующий сайт. Обойти можно лишь
персональным токеном с правами администратора, что для разовой настройки
избыточно. Поэтому `enablement` в workflow не используется — включаем
руками один раз.

**Пункта «GitHub Actions» нет в Settings → Pages.** Значит, Pages для
репозитория недоступны. Почти всегда причина одна: **репозиторий
приватный, а тариф — Free**; на бесплатном плане Pages работают только для
публичных репозиториев. Варианты:

- сделать репозиторий публичным — в стенде нет ни секретов, ни реальных
  данных: все краны, координаты и телеметрия вымышленные, а пара
  `demo`/`demo` и так описана в README как витрина, а не защита;
- перейти на GitHub Pro / Team, где Pages работают и для приватных;
- не публиковать вовсе, а показывать автономный HTML из
  `npm run build:standalone` — см. [08-local-run.md](./08-local-run.md).

### Версии actions

Actions закреплены на текущих мажорах: `checkout@v7`, `setup-node@v7`,
`configure-pages@v6`, `upload-pages-artifact@v5`, `deploy-pages@v5`.
Все они работают на Node 24. Старые мажоры (`@v4`/`@v5`) объявляли
runtime `node20` и выдавали предупреждение о его прекращении поддержки —
если оно снова появится, значит какой-то action отстал по версии.

Сборка проекта выполняется на Node 24 (`setup-node` → `node-version: 24`).

### Базовый путь

`base` для Vite берётся из переменной `BASE_PATH`, которую workflow
вычисляет из имени репозитория:

```bash
name="${GITHUB_REPOSITORY##*/}"
if [[ "$name" == *.github.io ]]; then
  echo "path=/"        # корневой сайт владельца
else
  echo "path=/$name/"  # проектный сайт в подкаталоге
fi
```

Локально переменной нет и `base` = `/`. Пути к ассетам нигде не
хардкодятся — иначе на Pages они отвалятся.

### Почему hash-роутинг

Pages отдаёт `404` на несуществующий путь и не умеет rewrite на
`index.html`. При обычных путях перезагрузка страницы на
`/monitoring/2483580` ломала бы приложение. Маршруты живут в хеше
(`#/monitoring/2483580`), сервер всегда отдаёт корневой `index.html`.

Файл `public/.nojekyll` отключает обработку Jekyll — на всякий случай,
чтобы Pages не съел служебные каталоги сборки.

## Проверка перед публикацией

- [ ] `npm run build` проходит без ошибок;
- [ ] `npm run preview` — вход `demo`/`demo`, оба раздела открываются;
- [ ] хронология: воспроизведение, перетаскивание курсора, «/» ,
      переключение «24 часа» / «Смена» / «7 дней»;
- [ ] «Архив»: листание дат назад, вперёд дальше сегодняшней не уходит;
- [ ] в Settings → Pages источником указан GitHub Actions (или репозиторий
      публичный, чтобы `enablement: true` сработал сам).
